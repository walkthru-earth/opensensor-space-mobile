# Sensor-agnostic app on a STAC contract

Research report, 2026-10-25. Status is proposal. Nothing here is implemented yet.

Goal. opensensor.space should stop being an air-quality app. Any station (air, weather, soil, water, noise, power) should sync, archive, chart and appear on Discover from a metadata contract alone, with no per-metric Kotlin. The contract is STAC JSON (Catalog, Collection, Item) plus a few standard extensions, one small custom extension and the station profile that fixes how a station catalog uses them, all released as stac-opensensor v0.1.0. Modules and types get generic names afterwards.

Inputs.
- Read-only audit of this repo (all 26 Gradle modules and the iOS targets).
- Read-only audit of `../aq-parquet` by this session, plus an independent audit by a Claude agent in an Orca worktree (branch `yharby/stac-firmware-audit`, commit `2b49114`, output kept uncommitted in `reports/stac-firmware-audit.md` of that worktree). A second independent pass checked that audit line by line against code, git history and the STAC specs (`reports/stac-firmware-audit-review.md`), and its corrections are folded in here (shared components, the CoreS3 and Waveshare board adapters. `firmware/esp-idf-n16r8` holds only build leftovers, no source, `docs/shared/*`, `product/*`).
- Online research on STAC 1.1, STAC extensions, stac-geoparquet, OGC SensorThings, OGC API Connected Systems and CF conventions. Sources are listed at the end.

---

## 1. Verdict

1. The app is about 80 percent ready for this. Sync, archive, verification, Parquet reading, daily rollups, tiers and Discover rendering are already generic. The AQ coupling sits in five places. These are the metric registry, the LIVE model, the Today, History and Devices screens, `:core:airquality`, and the Discover WHO legend.
2. The firmware already exposes almost everything a STAC Item needs. That covers station UUID, H3 cell and centre, country, UTC range from column statistics, schema name, firmware, dictionary SHA-256 and `field_id` per column. What it does not expose is the per-column dictionary itself. Units, procedure, validity and property URI exist only in `telemetry_fields.inc` and never reach the phone. The phone recognises a digest and falls back to a hardcoded `LiveProfile`.
3. STAC fits the envelope well (catalog, station, file, column list, units, statistics, i18n, Parquet mirrors). STAC does not model observation semantics such as validity gates, aggregation or health scales. Those need one small custom extension, released as stac-opensensor v0.1.0. The mapping to SensorThings (Thing, Datastream, ObservedProperty, Sensor) is kept in field names so a later SensorThings or Connected Systems adapter is a projection, not a redesign.
4. Recommended split, in three layers, as fixed by the [OpenSensor Station Profile](https://github.com/walkthru-earth/stac-opensensor/blob/a017edfa6cf5eb04f612c42f8473a52aef9d7f22/PROFILE.md).
   - Board template. Plain JSON with `"type": "OpenSensorTemplate"`, generated by the firmware build. It holds the columns and their meaning (core `unit` as UCUM, one ACDD role, `opensensor:` column fields), a default sample interval, instruments, and a `firmware` block with `live_keys`, `unit_labels`, `proto_min` and `dict`. Its identity has two keys. `dict` is the dictionary digest and is always known. `desc` is the SHA-256 of the exact generated template bytes and is optional.
   - Station Collection. STAC, written by an indexer that reads file footers on source.coop (bridge decision 12). Until that indexer exists, the phone writes it only for its own uploads. It is the template's columns plus titles and `opensensor:scale`, with `opensensor:scales`, extent, license and two `describedby` links, one to the firmware dictionary and one to the board template, each with `file:checksum`.
   - App profile. Owned by the app and keyed by `dict`. It holds `family`, `primary`, `hero`, `display_step` and `labels` in en and ar, and is never published as STAC.

   The phone resolves the board template by `desc` first and `dict` second (section 4.3), and joins it with the app profile into its core model. A digest with no app profile gets a default one derived from its template. The station profile is the rule set that says which extensions and column fields each station document must carry.

## 2. What exists today

### 2.1 Mobile app

Three separate metric descriptions exist, and they do not share a model.

| Description | Where | Source | Fields |
| --- | --- | --- | --- |
| `MetricSpec` | `core/history/.../Metrics.kt:23` | Hardcoded, 12 entries at `:120` | id, column, label (en), unit, kind, gate, healthScale, chartable, envelope, axisFloor, settleSeconds, property, basis, humidityColumn. The id is not always the column name. `pm25_epa` is derived from `pm25_cf1_ug_m3` plus `relative_humidity_percent` (`Metrics.kt:96-100`) |
| `LiveProfile` and `LiveSample` | `core/protocol/.../LiveProfile.kt`, `JsonModels.kt:133` | Hardcoded per known digest (10 digests), unreviewed vocabulary fallback since a139d80e | temperature source, humidity flag, key set and a per digest `temperatureKey` (`LiveProfile.kt:89`, `CORES3_LEGACY` reads `t` as board temperature). `LiveSample` is a fixed data class and drops unknown keys. Many fields are integers (`pms`, `n03` to `n10`, `bat`, `pct`, `chg`, `vbus`, `als`, `bstate`, `JsonModels.kt:140-177`) |
| `FeedProperty` | `core/publicfeed/.../Feed.kt:35` | Read at runtime from the Parquet key `dictionary` | id, label, unit, category, precision |

`FeedProperty` is the only data-driven one, and it is the seed of the new model.

Hard AQ logic.
- `Metrics.primary = PM25` (`Metrics.kt:129`) drives `validRows` for every bucket (`Aggregation.kt:46`). A soil station would report zero valid rows.
- `PMS_VALID = Gate("pms_status", 4)` and `PMS_SETTLE_S = 180` are board constants inside the registry (`Metrics.kt:87`).
- Coverage assumes one row every 10 s. `Resolution.expectedRows` (`Aggregation.kt:14`) and `HistorySeriesReader.kt:67` divide by 10.
- `archived_file.pmValidRows` (`ArchivedFile.kt:61`) is a per file count of rows with `pms_status == 4`. `ParquetIndexer` fills it, archive index repair carries it, and the Files metrics screen shows it.
- `:core:airquality` holds WHO 2021 scales (`HealthScale.kt:58-88`, looked up by the strings `pm25` and `pm10`), EPA PM2.5 correction and QC rules (not wired). `AirMood` and `NowReading` live in `:core:history` (`AirMood.kt:22`).
- Today picks cards from `DeviceCapabilities.showsParticles` and a `waveshare-sim7670g-telemetry-` prefix check (`DeviceCapabilities.kt:41`). A device without `pms` falls back to `EnvironmentCard`, a temperature and humidity card only (`TodayCards.kt:359-379`).
- History defaults to `PM25_CORRECTED` and snaps axes to WHO edges. Devices rows show PM2.5 and mood.
- Discover chips, labels and categories already come from the feed dictionary. Only the WHO legend and `isRawPm25` are hardcoded.

### 2.2 Firmware (`../aq-parquet`)

Columns are an X-macro per board.

```text
// firmware/esp-idf-cores3/bringup/telemetry_fields.inc
FIELD(name, physical_type, procedure, unit, validity, live_key)
FIELD(pm25_atmospheric_ug_m3, Int32, pmsa003, "ug/m3", pms_valid, "pm25")
FIELD(imu_temperature_c, Float, m5_imu, "degC", imu_temperature_read_finite, "imu_t")
```

- `field_id` is the 1-based line position, append-only. CoreS3 has 81 fields, Waveshare 62.
- `telemetry_contract.h` expands it to `kFields[]` with name, type, procedure, unit, validity, property URI (`urn:walkthru-earth:<board>:property:<name>`) and live key.
- `telemetry_dictionary_digest.h` is the SHA-256 of the raw `.inc` bytes. Any edit changes it, even a comment.

What reaches the phone.

| Channel | Content | Column semantics? |
| --- | --- | --- |
| BLE `info` and LAN `HELLO` | `{"proto":3,"fw":...,"schema":"cores3-telemetry-v5","cols":81,"dict":"<sha256>","station":"<uuid>",...}` | No, only the digest |
| BLE `live` and LAN push `0x49` | Flat `{live_key: value}`, 480 bytes max, floats as `%.1f` | No, keys only |
| Parquet schema | name, physical type, TIMESTAMP annotation, `field_id`, column statistics | No units or descriptions |
| Parquet footer (budget of 22 fixed, 7 location, 3 anchor and 32 board entries against a 64 entry cap, real use 37 on CoreS3 and 45 on Waveshare. The writer also hardcodes 64 and caps each value at 4096 bytes, `parquet_writer.cpp:593-600`. Going over fails the whole file, it does not truncate) | `schema_version`, `station_id`, `firmware`, `dictionary_version`, `dictionary_uri` (a GitHub `main` URL), `dictionary_sha256`, `acquisition_config`, H3 cell and resolution, country, code legends as free text | Pointer only |

Other firmware facts that shape the design.
- `info` is built in a 400 byte buffer (`ble_sync.cpp:56`) and the LAN `HELLO` frame has its own 400 byte cap (`wifi_link.cpp:1020-1031`). CoreS3 `info` is 287 bytes and Waveshare 301. If the BLE string overflows, BLE does not start at all, so any new key there must stay short.
- LIVE overflow is silent. Above 480 bytes `format_live` returns 0, nothing is published, and the last good snapshot keeps being served (`aq_logger.cpp:1614-1622`). The fixture's widest-value test is not the real worst case. A CoreS3 row with every float at full width can reach about 520 bytes, so real headroom for new CoreS3 LIVE keys is about 35 bytes.
- The released LIVE rule is the current one (`ble-sync-protocol.md:181`, `aq_logger_live.cpp`). Firmware never sends JSON null in LIVE. A key absent from one sample means no reading now (invalid, NaN, Inf, an out of range `utc`, text over 31 characters), so the app shows a dash or the stale value, never zero. A key not in the template's `firmware.live_keys` means the board lacks the field, so the app hides the card. Absent never means unsupported. Bridge decision 5 already decides a new rule. Only its write-up in `docs/shared/ble-sync-protocol.md` (aq-parquet #91) is pending, and the released rule stays the fallback until then. #185 does not code that part before the write-up lands.
- LIVE `utc` is nanoseconds while the file column `event_time_utc_us` is microseconds (`ble-sync-protocol.md:194`, `JsonModels.kt:137`).
- `field_id` is a stable join key only from schema v5. Commit `e166978` added field ids and changed position 9 from nanoseconds to microseconds in place, so older files reuse positions with different units.
- The same LIVE key can mean different things per digest. `t` is ambient on Waveshare, absent on CoreS3 v5, and the IMU die temperature on older CoreS3 dictionaries (`CORES3_LEGACY`). CoreS3 digest `22291d3a` covers two LIVE key sets (aq-parquet #31), one build sends the IMU temperature as `t` and one as `imu_t`. `pct` is an M5 power range on CoreS3 and a truncated gauge value on Waveshare. So the LIVE key to column map is per digest, never global. Firmware property URIs are board scoped today (`urn:walkthru-earth:cores3:property:pm1`), as `table-and-observation-model.md:138` intends. The owner decided that ObservedProperty ids are board neutral (section 3.5), and firmware #84 changes the FIELD prefix to match.
- Code values are layout, not labels. Waveshare `pms_status` adds `5 = model-mismatch` and owner decision #39 plans `6`. Under the LIVE stability rule (`ble-sync-protocol.md:208-214`) a new code value must move the `dict` digest.
- GATT characteristics including `info` need encryption (`ble_sync.cpp:1123-1134`), and LAN needs the token before `HELLO`. A device-served descriptor is post-pairing only, so it must hold board facts only, never station or location data.
- CoreS3 `ambient_temperature_c` and `relative_humidity_percent` (`telemetry_fields.inc:79-80`) are always null because of the SHT20 address collision. The app shows the board IMU temperature (`imu_t`) instead. Waveshare gets valid `t` and `rh` from the PMS5003T.
- The only per-column vocabulary that leaves the device is free text in board footer keys (`pms_status`, `gauge_status`, `sensor_model` and similar). Waveshare also reports vendor and model on config page 0. CoreS3 reports no sensor model at all.
- `docs/shared/table-and-observation-model.md:40` is stale. It says Waveshare v3 has 56 fields, the current table has 62.

No opcode returns the dictionary (`ble-sync-protocol.md:224-241`). A full dictionary JSON can be produced on the host by `tools/test_telemetry_contract.py --dictionary-out` (it runs the fixture binary as `<exe> dictionary`). The same fields are also printed at runtime by the serial `parquet schema` console command (`aq_logger.cpp:2522-2534`), so they are in flash, just not on BLE or LAN. The JSON is shape `{schema, schema_version, dictionary, firmware, sha256, fields:[{name,type,procedure,unit,validity,property,field_id,live}]}`, about 15.4 KB minified for CoreS3, and is not committed or published.

Shared-code limits that block non-AQ boards.
- 96 columns max (`parquet_writer.h:8`). Types are Int32, Int64 and Float only.
- Footer literals `sample_interval_ms = "10000"` and `row_group_rows_max = "90"`. `deployment_id` and `calibration_id` are always `"unknown"`.
- LIVE floats at one decimal, integer fields as integers. pH 7.25, soil EC or accelerometer values under 0.05 g lose precision. Changing the format is a wire change.
- BLE name prefix. Firmware #90 moves every board to the `OS-` prefix and the `os-xxxx` mDNS host (bridge decision 6). The app scans by GATT service UUID only and has no name prefix, shipped in lockstep with #90. The `sensor.*` config keys assume one PMS-style module.

`docs/shared/table-and-observation-model.md` already decided the layering. Immutable wide Parquet stays the raw archive, a versioned dictionary carries meaning, and SensorThings and Iceberg are later host-side projections. It proposes Thing = station, Sensor = procedure, Datastream = column contract, ObservedProperty = exact quantity and processing variant, feature of interest = local air or the board itself. No code in either repo reads or writes STAC today.

## 3. Research findings

### 3.1 STAC core 1.1 (released Sept 2024)

- Common metadata now has `unit`, `data_type`, `nodata`, `statistics` (`minimum`, `maximum`, `mean`, `stddev`, `count`, `valid_percent`) and a generic `bands` array that "need not be spectral". `unit` should be UCUM or UDUNITS-2.
- Common metadata also has `instruments`, `platform`, `constellation`, `mission`, `keywords` and `roles`.
- Best practices for static catalogs. Use relative structural links, name files `catalog.json`, `collection.json` and `<id>.json`, keep sub-catalogs under about 1 MB, and partition when there are tens of thousands of children.
- STAC targets spatio-temporal data. Our data always has an H3 cell, so every Item has a geometry (the H3 cell polygon, never the raw fix).
- Ranges use `start_datetime` and `end_datetime`, which suits per-file or per-day Items.

### 3.2 Extensions that fit

| Extension | Version, maturity | Use here |
| --- | --- | --- |
| Table (`table:`) | v1.3.0, Pilot | `table:columns` (name, type, description, plus common `unit`, `roles`, `statistics`), `table:primary_datetime`, `table:row_count`. The column list sits in the station Collection's `item_assets.data`, and each day Item repeats only the columns it has statistics for. Upstream proposals table#16 (`field_id`) and table#17 (validate common metadata in columns) are open |
| Datacube (`cube:`) | v2.3.0, Candidate | Not used by the station profile. `cube:variables` could give clients like xarray a richer view of the same columns, but `cube:dimensions` becomes required and a station dimension needs a custom type, never `spatial` |
| CF (`cf:`) | v1.0.0, Proposal | `cf:standard_name` on columns. Gives a shared vocabulary, for example `mass_concentration_of_pm2p5_ambient_aerosol_particles_in_air` (canonical unit kg m-3). Column use is proposed upstream in cf#11 |
| Classification | v2.0.0, Pilot | `classification:classes` with `value`, `name`, `description`, `color_hint`, `nodata`. Fits code columns such as `pms_status` and `clock_status`, which are free-text legends today. Classes inside table columns are proposed upstream in classification#55 |
| Grid (`grid:code`) | v1.1.0 | Item scope only. `H3-<cell>` is allowed as a proprietary designation. Use only the owner's privacy-capped cell |
| Anonymized Location (`anon:`) | v1.0.0 | `anon:size` and `anon:warning` on Items, so clients know the geometry is the owner's coarse cell and not the station position |
| Language (`language`, `languages`) | v1.0.0, Proposal | Not used. It translates whole documents and has no inline form, so en and ar labels sit in scale step label maps and in the app profile |
| File (`file:`) | v2.1.0, Stable | `file:size`, `file:checksum` on Parquet assets. The phone already verifies size and CRC-32. `file:checksum` on the two `describedby` links carries the dictionary digest and the board template digest |
| Version | v1.2.0, Candidate | `version`, `deprecated`, predecessor and successor links between Collection revisions |
| Contacts, Scientific | Proposal, Stable | Owner and citation for CC BY 4.0 publishing |
| Time Series (`ts:`) | Archived Jan 2023 | Do not use |
| Moving Features | WIP, unreleased | Not needed, stations are fixed |

No registered STAC extension describes in-situ station observations, validity gates, aggregation rules or health scales. That gap is why a small custom extension exists, see section 4.4. The station profile at the end of section 4.4 then fixes which of these extensions each station document declares.

### 3.3 stac-geoparquet

- Spec v1.1.0. One row per Item, required columns `id`, `geometry`, `bbox`, `links`, `assets`, `stac_extensions`.
- Parquet footer key `stac-geoparquet` holds `version` and `collections` (a map of id to full Collection JSON). This makes a Parquet file self-describing.
- A Collection can point to its GeoParquet mirror through an asset with role `collection-mirror` and type `application/vnd.apache.parquet`.
- Relevance. The public feed on source.coop can ship one `items.parquet` per station collection instead of thousands of small Item JSON files, and the app's existing `:core:parquet` reader can read it over HTTP range requests.

### 3.4 Observation standards for comparison

- OGC SensorThings API. Thing has Locations and Datastreams. Each Datastream links one Sensor and one ObservedProperty, carries `unitOfMeasurement` and `observationType`, and holds Observations. V2 is still a draft. The firmware doc already says not to claim compliance.
- OGC API Connected Systems Part 2 (published 2025-07) with SensorML 3.0 and SWE Common 3.0 JSON. Datastreams describe record schemas with definition URIs and UoM codes. It is complete but heavy for a phone app and a microcontroller.
- No published STAC to SensorThings crosswalk was found. The sta2stac project (KIT) exposes STA servers through STAC but documents no field mapping we could reuse.

Conclusion. Use STAC for discovery and file-level description. Borrow SensorThings names (Station, Datastream, ObservedProperty, Sensor) for our own types, so a later STA or Connected Systems endpoint is a straight projection.

### 3.5 Units and vocabularies

- STAC `unit` accepts UCUM or UDUNITS-2, and the CF extension README prefers the same two. This design puts the UCUM code in core `unit`, one unit system with no second field. The firmware label stays in the board template under `firmware.unit_labels`, only where it differs from the UCUM code.
- UCUM is case-sensitive. `ug/m3` is valid. `degC` becomes `Cel`. `count/0.1L` becomes `{particles}/dL`. `g` in the CoreS3 IMU columns means standard gravity, which is `[g]` in UCUM (plain `g` is gram). `byte` is `By`. `YYYYMMDD` and `hhmmss` are formats, not units. `us_since_unix_epoch` is a time column described by `table:primary_datetime`.
- CF names need care. `mass_concentration_of_pm2p5_ambient_aerosol_particles_in_air` fits the `atmospheric` columns only, not the CF=1 columns. `air_temperature` must not be used for `imu_temperature_c`.
- Keep the firmware label as written in the board template and put the UCUM code in the STAC `unit`. Never rewrite the firmware string, because it is part of the digest.
- `opensensor:property` is the ObservedProperty id, and it is board neutral (owner decision, design rule 4). Use a NERC P07 term first, such as `http://vocab.nerc.ac.uk/collection/P07/current/YUDG9DXK/` for PM2.5. Next comes `http://vocab.nerc.ac.uk/standard_name/<cf name>/` for an exact CF match. Otherwise use `urn:walkthru-earth:property:<quantity>`, such as `urn:walkthru-earth:property:pm25_cf1_mass_concentration`. The id never names the board. The board and sensor model (PMSA003 on CoreS3, PMS5003T on Waveshare) live in `opensensor:procedure`. `cf:standard_name` exists only on the three atmospheric PM columns, so it cannot be the only join key. Add `cf:standard_name` where CF has one. Leave it empty otherwise, as the CF extension requires.
- stac-opensensor `PROFILE.md:96` at the `v0.1.0` tag still has the board scoped fallback `urn:walkthru-earth:<board>:property:<column>`, which conflicts with this rule. Its main branch adopts the board neutral rule in commit `a017edf`, but no tag carries it yet (section 8).

## 4. Proposed contract

### 4.1 Mapping

| Our concept | SensorThings | STAC | Today |
| --- | --- | --- | --- |
| Network root | none | Catalog `opensensor.space` | none |
| Firmware dictionary (one digest) | Sensor plus ObservedProperty set | First `describedby` link on the station Collection, with the digest in `file:checksum` | `telemetry_fields.inc` |
| Board template (one digest) | Sensor plus Datastream set | Not STAC. Plain JSON with `"type": "OpenSensorTemplate"`, mirrored at a proposed `templates/<schema>.json` (section 4.6, open question 15), second `describedby` link on the station Collection with its SHA-256 in `file:checksum` | `LiveProfile`, fact parts of `MetricSpec` |
| App profile (one digest) | none | None, a plain JSON file inside the app, never published as STAC | `LiveProfile`, presentation parts of `MetricSpec` |
| Station | Thing | Collection per station UUID that lists the station profile in `stac_extensions`, `extent` from data (spatial `bbox` is the owner's H3 cell bounds), `license`, `instruments`, `keywords`, `opensensor:scales`, `opensensor:sample_interval_s` as the default interval, columns in `item_assets.data.table:columns` | station UUID, footer keys |
| Column | Datastream | One entry in `item_assets.data.table:columns` with core `unit`, exactly one value in core `roles` and `opensensor:` column fields, copied from the template plus `title` and `opensensor:scale` | `FIELD(...)` line |
| Quantity | ObservedProperty, board neutral (section 3.5) | `opensensor:property` URI from shared vocabulary or `urn:walkthru-earth:property:<quantity>`, plus `cf:standard_name` where CF matches exactly | `property_uri`, board scoped today |
| Sensor model | Sensor | `opensensor:procedure` on each column, never part of the property id | `procedure` |
| Day of data | none | Item per Hive day partition, geometry = H3 cell polygon, `grid:code`, `anon:size` and `anon:warning`, `start_datetime` and `end_datetime` covering the UTC day with `datetime` null | `station=/year=/month=/day=` |
| Parquet file | none | Asset with `file:size`, `file:checksum`, roles `data`, `table:row_count` and core `statistics` per column | file in archive |
| Discover aggregate | none | Collection `discover-cells` with assets per `h3_res`, `table:columns` from the feed dictionary | `FeedProperty` and `manifest.json` |

Why Item per day with one asset per file. The upload unit is one closed file of at most 1 hour (bridge decision 16, rotation 600, 900, 1800 or 3600 s, never longer). A station writes about 35,000 files per year at 15 minute rotation, so an Item per file would flood the catalog. Per-day Items give 365 per year, line up with the Hive `day=` partition and keep catalogs well under the 1 MB guidance. The day Item gains one asset per file as files land, so a near real time reader never waits for the day. A file is uploaded only with UTC times on its rows, because STAC needs a start and end and device files written before a clock sync have null UTC. A full day has 86400 divided by the interval rows, 8640 at today's 10 s. The interval is the per file footer `sample_interval_ms`, never an assumed 10 s, because aq-parquet #90 makes it runtime config. RTC-restored days are dated but approximate, which the day Item shows through the core `statistics` of its `clock_status` column. A station UUID lives in NVS and follows the board when it moves, so the H3 cell and time range tell deployments apart.

### 4.2 Who owns what

| Fact | Owner | Delivery |
| --- | --- | --- |
| Column name, type, order, `field_id`, procedure, code values, instruments | Firmware `telemetry_fields.inc` (`dict`) | Board template, generated at build time into `opensensor:` column fields |
| Sample interval | Firmware config (aq-parquet #90) | Per file footer `sample_interval_ms` is the truth. The template value is only the default |
| `firmware.live_keys`, `firmware.unit_labels`, `firmware.proto_min` and `firmware.dict` | Firmware | Board template only, never in STAC. The `dict` digest reaches STAC as `file:checksum` on the dictionary `describedby` link |
| Code values (for example `pms_status` 0 to 5) | Firmware `telemetry_fields.inc` side, a new value moves `dict` | Board template, as `classification:classes` |
| UCUM code for core `unit`, `cf:standard_name`, ACDD role for core `roles`, aggregate, plausible range, settle seconds, `valid_when`, sensor make and model, names for code values | Today mobile Kotlin (`Metrics.kt`, `LiveProfile.kt`). After the epic firmware `telemetry_semantics.inc` (aq-parquet #84) | Same board template, generated by aq-parquet #85. #84 copies today's Kotlin values and invents none |
| Labels (en, ar), display step, family, default columns, hero card | App profile, owned by this app | Plain JSON keyed by `dict`, bundled in the app, never published as STAC |
| Health scales and colours | Scale registry in this app | Written into each station Collection as `opensensor:scales`, with `opensensor:scale` on each column that uses one |
| Station metadata (column titles, H3 cell, country, license, owner contact) | Phone at provisioning | Station Collection and day Items written by the indexer that reads file footers (bridge decision 12). Until it exists, the phone writes them only for its own uploads, and only when the owner enables publishing |
| Statistics per day | Phone | Computed from Parquet footers into core `statistics` on Item columns, already done by the daily builder |

Keeping labels and health scales out of firmware means WHO, EPA or national scale updates, new translations and new colour rules ship without a flash. While #183 to #186 are open, no semantic value (settle, gates, ranges, units, keys) in `Metrics.kt` or `LiveProfile.kt` changes, so #84 and the mobile parity tests compare like with like.

### 4.3 Delivery paths

1. Bundled templates first (#184). Only for the current firmware digest of each board (CoreS3 v5, Waveshare v5), write a hand-checked board template from the LIVE key sets in aq-parquet `tools/fixtures/live_keys/*.json` (that repo, not this one) plus the host dictionary JSON, and write the matching app profile by hand. The CoreS3 template comes from stac-opensensor `a017edf` or later, never the `v0.1.0` bytes. When #91 moves `dict` on both boards, the bundle follows the new digests posted in the bridge. These templates are provisional and keyed by `dict`, because hand JSON never hash matches a generator's `desc`. Store them as raw files, so the bytes firmware #86 publishes can drop in verbatim later. Validate each template against the template schema (`https://walkthru-earth.github.io/stac-opensensor/v0.1.0/template.json`). The phone copies the template columns into each station Collection it writes, adding titles and `opensensor:scale`. No firmware change. This replaces `LiveProfiles.resolve` and `Metrics.all`. Legacy `LiveProfile` digests and the `VOCABULARY` fallback are deleted, not ported (bridge decision 9).
2. Published templates. Firmware #86 publishes generated template bytes in aq-parquet `docs/shared/templates`, only for the current digest of each board. The app copies those bytes into its bundle verbatim and never rewrites them. Where else templates are mirrored (for example source.coop) is open, see section 8. App profiles are not published. Change the footer `dictionary_uri` from a GitHub `main` URL to a pinned commit URL, as the template's own `describedby` link already does.
3. Device-served descriptor (optional). Add read-only opcode `0x11 GET_DESCRIPTOR` (opcodes end at `0x10`) and frame type `0x4F DESCRIPTOR_CHUNK` (frame types end at `0x4e`, `ble_sync.h:43-86`). Use a request per chunk, `GET_DESCRIPTOR(offset u32, length u16)`, answered with one frame up to the negotiated size (512 on BLE, 1024 on LAN), so the app can re-request lost ranges. The `CONFIG_CHUNK` style does not fit, because it is BLE only, sends 128 byte slices with no end frame, and Android drops bursts of 16 to 18 notifications. Advertise support with `"desc":"<16 hex prefix>"` in `info` (313 and 327 bytes, under both 400 byte caps). The app gates on `desc` in `info` and never probes, since old firmware answers `0x11` with ERROR 11. It restarts the download if `desc` changes midway, and handles an offset past the end and a short final chunk. It verifies the SHA-256 over the exact received bytes, never after re-encoding with kotlinx serialization. `AqJson` ignores unknown keys. A new frame type is safe only because it is never sent unsolicited, since `Frames.kt:499` throws on unknown types. An app with that descriptor cached skips the download.
   - The descriptor is the board template, never app profile labels or scales. Its own digest (`desc`) is the SHA-256 of the generated template bytes, the same value as `file:checksum` on the station Collection's template link. `dict` keeps covering only `telemetry_fields.inc`, so released app profiles stay valid while units and column semantics evolve. `desc` needs the same three gates as `dict` today (`tools/build-idf-board.sh:19-23` and both contract tests), or it will drift.
   - Cost. Today's bare CoreS3 dictionary is already 15.4 KB minified (about 1.9 KB zlib). A full board template with UCUM units, CF names, roles and code classes for all 81 columns is likely 25 to 40 KB raw. The app slot is 6 MB on both boards, so that is still under 1 percent. No ESP-IDF image size is recorded yet, the 1.4 MB figure is from Arduino builds. RAM cost is near zero because chunks stream from `.rodata` into the existing frame buffer. Serving raw JSON avoids a gzip dependency on the phone.
   - Footer. Do not embed the board template in each Parquet file. A full Collection exceeds the 4096 byte value cap, and `table-and-observation-model.md:114` already rules out repeating descriptions in every small file. Add two keys instead, `opensensor:template_href` (pinned URL or `urn:opensensor:template:<board>:<desc sha>`) and `opensensor:template_sha256`, about 260 bytes per file. Pass them as board metadata, which only counts against the 32 board slots (CoreS3 goes from 5 to 7, Waveshare from 13 to 15). No budget change is needed. Never raise `kFooterMetadata` alone, because the writer's literal 64 would then fail every file.
4. Self-describing exports. When the phone uploads a closed file or exports a Parquet file, write the station Collection into the footer under the `stac-geoparquet` key, `collections` map. A file then stands alone on source.coop or in DuckDB. `DailyParquetBuilder.kt:488` copies a fixed key list (`COPIED_METADATA`), so it must also copy `opensensor:template_href` and `opensensor:template_sha256` or they never reach published files. No `stac:*` footer keys exist. `sample_interval_ms` is already in that list.

Resolution on the phone.
- Template identity is `dict` (always known) plus `desc` (optional). Once a template carries `desc`, resolve by `desc` first, then `dict`, because a unit or range fix changes `desc` without `dict`. Bundled hand templates are found by `dict` only. App profiles stay keyed by `dict`.
- Sources in order. The device descriptor (only when `info` carries `desc`), then the bundled templates. Other mirrors are not decided yet.
- Keys map to columns per digest through `firmware.live_keys`, never through a global vocabulary. CoreS3 `22291d3a` once carried two LIVE key sets (aq-parquet #31), but it is a legacy digest and is no longer bundled, so no current template needs more than one key per column.
- A digest with a template but no app profile gets a default profile derived from the template. `primary` is the first `physicalMeasurement` column, labels come from column titles or names, and there is no hero card. A bundled app profile overrides it.
- A digest with no template still syncs and shows raw column names and raw units.

### 4.4 Custom extension `opensensor:`

The extension is released as v0.1.0 in walkthru-earth/stac-opensensor, with its JSON Schema at `https://walkthru-earth.github.io/stac-opensensor/v0.1.0/schema.json`. It only defines what STAC core and existing extensions do not cover, and `docs/overlap-review-2026-10-25.md` there explains each decision. Field names follow SensorThings words. All fields are optional, so a station Collection with only `table:columns` and `unit` still renders as plain numbers with raw names.

Column fields (inside `table:columns` entries).

| Field | Type | Meaning | Replaces |
| --- | --- | --- | --- |
| `opensensor:property` | string URI | Observed property, board neutral. A NERC P07 term first, then `http://vocab.nerc.ac.uk/standard_name/<cf name>/` for an exact CF match, else `urn:walkthru-earth:property:<quantity>`. The board and sensor go in `opensensor:procedure` | `property_uri` |
| `opensensor:procedure` | string | Sensor model or procedure id that produced the column | `procedure` |
| `opensensor:field_id` | integer | Parquet `field_id`, join key to Iceberg, schema v5 and later | none |
| `opensensor:valid_when` | `{column, equals}` or `{column, finite: true}` | Validity gate | `Gate`, `PMS_VALID` |
| `opensensor:settle_s` | number | Warm-up seconds after power on | `settleSeconds` |
| `opensensor:aggregate` | `mean`, `minimum`, `maximum`, `sum`, `point`, `mode` today | How tiers roll up, in CF `cell_methods` words. `point` is an instantaneous read, `mode` is for coded columns. The list is not exhaustive. The app parses unknown values and treats them as `point`, never through an exhaustive Kotlin enum that fails on them | implicit mean |
| `opensensor:plausible_range` | `[min, max]` | Plausible range for QC flags and axis floor. Values outside are suspect, not masked | `axisFloor`, `QcRules` |
| `opensensor:scale` | id | Id of a scale in `opensensor:scales` | `healthScale` |
| `opensensor:derived` | `{from: [...], method: URI}` | Derived column computed on the phone, for example EPA correction | `basis`, `humidityColumn` |

| Field | Meaning |
| --- | --- |
| `opensensor:scales` | Map of scale objects keyed by id. Each has `source` (citation URL), `steps` (`upper`, `label` as a string or an en and ar map, `color_hint`), an optional `unit` and an optional `guideline` line |

### 4.6 Catalog layout on source.coop

Bridge decisions 12, 13 and 16 (2026-10-26) fix the main points.
- The upload unit is one closed file of at most 1 hour (rotation 600, 900, 1800 or 3600 s), never a day. Board uploads (aq-parquet #81) send each file as soon as it closes. The phone path (#181, #190) uploads closed files as they arrive and never holds data back to build a day file.
- Files keep the existing archive layout `station=<uuid>/year=YYYY/month=MM/day=DD/data_HHMM_<boot>_<first>-<last>-<attempt>.parquet`, under one board prefix with no `raw/` prefix.
- Each file stands alone, with a full footer (`dict`, `opensensor:template_sha256`, `sample_interval_ms`, station) and UTC times, so a consumer can use it without waiting for the day.
- Files describe themselves, so one indexer that reads footers on source.coop builds the station Collection and day Items. The day Item gains one asset per file as files land. Until the indexer exists, the phone writes STAC for the files it uploads.
- Day compaction is optional, comes later and lives under a separate prefix. Compacted files are never mixed with the raw hour files under one prefix, or readers count rows twice.

Edge cases.
- A reboot inside an hour gives two files for that hour, with different `<boot>`. Both are valid assets.
- A board that was offline uploads many past hours at once. Order by file times, never by upload time.
- A re-upload with a new `<attempt>` replaces the same rows. Consumers deduplicate by station plus time.
- `FLUSH` gives a short file, which is fine.

The tree below is a proposal beyond those points. App profiles are not part of the layout, they ship inside the app.

```text
opensensor-space/
  catalog.json                       STAC Catalog, one child link per station
  templates/
    <schema>.json                    board template, cached forever by digest
  station=<uuid>/
    collection.json                  station Collection, columns in item_assets, describedby links to the dictionary and the template
    year=YYYY/month=MM/day=DD/
      data_HHMM_<boot>_<first>-<last>-<attempt>.parquet   one closed file of at most 1 hour
      item.json                      day Item, one asset per file
    items.parquet                    stac-geoparquet mirror of the day Items
  <compaction prefix>/              optional later day files, prefix not decided
  discover/
    collection.json                  H3 aggregates, replaces manifest.json
    cells/h3_res=<n>/data.parquet
```

Only stations whose owners enable CC BY 4.0 publishing appear. Geometry is always the H3 cell polygon at the owner's chosen resolution, never the phone fix.

## 5. App changes

### 5.1 New core model

Create the planned `:core:model` (pure `commonMain`) with `Station`, `BoardTemplate`, `AppProfile`, `Datastream`, `ObservedProperty`, `Scale`, `ScaleStep`, `ValidityGate`, `Aggregate`, `Role` and `Family`. `Aggregate` and `Role` keep unknown values instead of failing (an unknown aggregate reads as `point`). A `Datastream` has its own id and a list of source columns, because a derived datastream such as `pm25_epa` reads `pm25_cf1_ug_m3` and `relative_humidity_percent`. New model code does not bake in the `AQ-` name prefix. It scans by GATT service UUID or the board prefix, in lockstep with aq-parquet. `BoardTemplate` and each `Datastream` carry only template facts, `AppProfile` carries only the app's presentation choices, and `Station` joins one template, one app profile and the station Collection's titles and scales. Add `:core:catalog` to parse board templates and station Collections (kotlinx.serialization, unknown fields ignored), validate templates against the template schema and station documents against the station profile, and resolve the board template by digest (device descriptor, then bundled template, then source.coop template, cached forever by digest).

Then replace the three current descriptions.

### 5.2 Family plugins

AQ science becomes one plugin, not core logic. Move `:core:airquality` to `:family:air` with `AirMood`, the peacock hero, EPA correction (as an `opensensor:derived` method), QC rules and the Plantower batch candidate. Core only knows a `FamilyPlugin` interface with an optional hero card, derived-column methods and QC hooks. A device with no plugin still gets generic cards, charts and Discover cells.

### 5.3 Screens

- Today. Cards are generated from the app profile `primary` list and the remaining `physicalMeasurement` and `auxiliaryInformation` datastreams, grouped by category. The air family supplies the mood hero card. A card hides only when its key is not in the board's `live_keys`.
- History. The default metric is the first column of the app profile `primary` list. Axes use the datastream's scale when there is one, otherwise `opensensor:plausible_range` or the data range.
- Devices. The row glance shows the first primary datastream with its scale colour or a neutral chip.
- Discover. The WHO legend becomes "the property's scale when the station Collection has one". Category chips already come from data.

## 8. Open questions for the owner

1. Item granularity. Decided in bridge decision 16. One day Item per station and UTC day, with one asset per uploaded file of at most 1 hour. Files without UTC times are never uploaded.
2. Collection shape. Decided by the station profile. One Collection per station keeps per-station licensing and extents, and the per-schema facts the firmware audit wanted in one place live once in the board template. Discover keeps its own aggregate Collection.
3. Health scales live in station Collections as `opensensor:scales`, filled from the app side scale registry (recommended). Can firmware ship them too.
4. Name of the custom extension prefix. `opensensor:` is released as v0.1.0 in walkthru-earth/stac-opensensor. A neutral prefix such as `obs:` would help other networks adopt it.
5. Is `Station`, `Datastream`, `BoardTemplate`, `AppProfile` acceptable as the type vocabulary, or do you prefer `Feed` for Datastream.
6. Should the `GET_DESCRIPTOR` opcode be built, or are bundled plus published board templates enough for now.
7. Which scale ships first for PM, WHO 2021 (current app default) or US EPA AQI, and who reviews the Arabic labels.
8. Units. Decided, UCUM codes in core `unit`, one system only. The firmware label stays in the board template under `firmware.unit_labels`.
9. Public H3 resolution. Section 4.4 sets the rule, the owner's chosen cell (default 5) governs every public document. Open is whether stac-opensensor should change its resolution 8 convention to match.
10. Is `pms_status 6` (#39) planned before or after the descriptor, since it moves `dict`.
11. For LoRa-only boards (PR #68), is a board template lookup by digest on source.coop enough, since they cannot use the opcode.
12. Accra demo timing. P1 and P2 change internals only and could land before the demo. P3 changes visible screens and is safer after.
13. stac-opensensor release. Board neutral property ids are decided (section 3.5) and on stac-opensensor main at `a017edf`. `PROFILE.md:96` at the `v0.1.0` tag still has the board scoped fallback, which conflicts. The profile's single `assets.data` rule for day Items also predates per file assets (bridge decision 16). A stac-opensensor change, a tagged release that carries both, is pending an owner decision.
14. Boards that upload directly (aq-parquet #81). Decided in bridge decision 12. One indexer that reads footers on source.coop writes the station Collection and day Items. Until it exists, the phone writes STAC for the files it uploads (section 4.6).
15. The source.coop prefix layout. Decided in bridge decisions 13 and 16. Uploaded files keep the archive layout under one station prefix, and optional day compactions live under a separate prefix that is not named yet (section 4.6). Still open is whether source.coop mirrors board templates, for example at `templates/<schema>.json`.
16. Parquet files already on phones. Decided in bridge decision 14. The app does not need to read them, they are wiped after the matched reflash.
